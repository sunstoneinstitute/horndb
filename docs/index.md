# HornDB docs index

This is the human-facing entry point for the docs directory, and the first stop for coding agents using progressive discovery.

## Start here

- [`../README.md`](../README.md) — project overview, status, architecture, and build/test commands.
- [`specs/README.md`](specs/README.md) — index of the authoritative SPEC documents.
- [`specs/AGENTS.md`](specs/AGENTS.md) and [`plans/AGENTS.md`](plans/AGENTS.md) — naming and frontmatter rules: specs are `SPEC-NN-<slug>.md`, plans are `PLAN-NN-MM-<slug>.md` (`NN` = origin spec, `00` if none), both with `status:` / `date:` / `scope:` frontmatter.
- [`adr/README.md`](adr/README.md) — Architecture Decision Records: the *why* behind the cross-cutting choices (the six SPEC-00 bets plus major tech decisions).
- [`../TASKS.md`](../TASKS.md) — live follow-up list and current gaps.
- [`benchmarks.md`](benchmarks.md) — performance targets, baselines, current measured results, and reproduction commands.

## Docs in this directory

- [`architecture.md`](architecture.md) — single-page architecture map across all SPECs, with a **Status** field (implemented / specified / planned / deferred) per subsystem and feature. Read this to see what exists today; kept in sync with `../TASKS.md`.
- [`architecture/`](architecture/wcoj.md) — per-subsystem deep-dive architecture guides (distinct from the single-page `architecture.md` status map). Currently: [`architecture/wcoj.md`](architecture/wcoj.md) — how `horndb-wcoj` (SPEC-03) evaluates a BGP with a Leapfrog Triejoin: the trie-iterator stack, single-variable leapfrog intersection, depth-first driver, and the k==2 SIMD intersect fast path. Opens with a from-scratch soft introduction to WCOJ; read before touching the seek path or descent/ascent bookkeeping. And: [`architecture/simd.md`](architecture/simd.md) — how `horndb-simd` (SPEC-12) chooses a SIMD kernel per host (the `forced → cap → known-CPU table → calibration → static` ladder), which engine operations are SIMD-enabled (WCOJ intersect/seek, storage partition-scan/gather), the `intersect` skew gate, and the two policy knobs (ISA cap + auto-tune) seeded via `configure` from `[simd]` config (`HORNDB_SIMD__MAX_ISA`, `HORNDB_SIMD__AUTOTUNE`). Read before touching kernel selection or adding a CPU table row.

- [`research/optimizer-sota.md`](research/optimizer-sota.md) — cited state-of-the-art reference behind SPEC-23's cardinality estimator and cost-based join planner: RDF-native estimation (Characteristic Sets, SumRDF), pessimistic/degree-sequence bounds (bound sketch → SafeBound → LpBound), sampling (Wander Join), and hybrid WCOJ execution/ordering (Freitag cyclic-core hybrid, Graphflow i-cost, Free Join/COLT, EmptyHeaded GHDs, AGM). The "why these algorithms" for [PLAN-23-03]/[PLAN-23-04]; read before implementing the `Stats` seam, the estimator, or cost-based ordering.
- [`specs/SPEC-23-unified-ir.md`](specs/SPEC-23-unified-ir.md) — the Stage-2 flagship (epic [#185](https://github.com/sunstoneinstitute/horndb/issues/185)): a *single* logical IR expressing query **and** reasoning, so the optimizer can jointly decide join order **and** reasoning strategy (materialize vs. rewrite vs. delegate) on one cost scale. The optimizer framework is the foundation that ships first — logical IR + flat n-ary BGP, binding/type lattice, typed toggleable pass registry, layered `Stats` seam, one cost-based ordering stage (structural WCOJ-vs-hash routing + a unified i-cost model, per [`research/optimizer-sota.md`](research/optimizer-sota.md)), synthesizing Oxigraph `sparopt` / DuckDB / ClickHouse; reasoning enters the same IR later as rewrite passes + delegate nodes (§5.8), pulling in magic-sets/backward-chaining (SPEC-03 F4/F5) + SPEC-07 backward mode. Read before turning the Stage-1 planner stubs (`crates/wcoj/src/planner.rs`, `crates/sparql/src/plan/planner.rs`) into a real optimizer; realizes SPEC-03 F2/F6 and consumes SPEC-08 F2 (`PlanAdvisor`). See `architecture.md` §16 and the [Stage-2 investment epics](architecture.md#stage-2-investment-epics) table.
